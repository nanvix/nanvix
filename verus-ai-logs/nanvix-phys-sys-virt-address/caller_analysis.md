## Caller Expectations

### `VirtualAddress` (the type)
- Callers assume: it is a transparent newtype wrapping a single `usize` (pointer-sized;
  a `static_assert::assert_eq_size!` enforces 4 bytes on 32-bit targets). It is `Copy`,
  cheap, and behaves like an ordered integer for `==`, `<`, `min`, etc.
- Used as a type parameter for generic containers: `MemoryRegion<VirtualAddress>`,
  `TruncatedMemoryRegion<VirtualAddress>`, `PageAligned<VirtualAddress>`,
  `PageTableAligned<VirtualAddress>` (kimage.rs, mmio/region.rs, vmem.rs).
- Callers don't care about: any internal representation beyond "it holds one `usize`";
  no internal flags, tags, or bookkeeping are observed.

### `VirtualAddress::new(value: usize) -> Self`
- Callers assume: the result is a `VirtualAddress` whose raw value is exactly `value`,
  with no validation, masking, or transformation. Being `const fn`, it is used in
  `const` context (e.g. `const MMAP_BASE: VirtualAddress = VirtualAddress::new(...)`
  in `sysalloc/src/vaddr.rs:31`).
- The dominant caller pattern is **raw arithmetic + reconstruct**, e.g.
  `VirtualAddress::new(src.into_raw_value() + copy_size)` (vmem.rs:1070-71, 1247-48,
  1381-82) and `VirtualAddress::new(dest.into_raw_value() + s.len())` (manager/mod.rs).
  This requires the exact round-trip identity `new(a).into_raw_value() == a`.
- Callers also build addresses directly from pointers/integers:
  `VirtualAddress::new(ptr as usize)`, `VirtualAddress::new(raw_vaddr)`.
- Callers don't care about: any error path (there is none — it is infallible) or
  alignment (callers align explicitly afterward when needed).

### `VirtualAddress::from_raw_value(raw_addr: usize) -> Self` (inherent)
- Callers assume: identical semantics to `new` — an infallible constructor that stores
  `raw_addr` verbatim. It is the idiomatic "make an address from this integer/pointer"
  entry point (kimage.rs module-region bases, elf loader, dlfcn symbol resolution,
  stack/segment setup, syscall munmap, test fixtures).
- Same round-trip reliance: `VirtualAddress::from_raw_value(base.into_raw_value() +
  capacity)` (syscall/safe/mem/segment.rs:108,217,231) — depends on
  `from_raw_value(a).into_raw_value() == a`.
- Used as a function pointer in `.map(VirtualAddress::from_raw_value)` (checked_add /
  checked_sub internally), so its `usize -> Self` signature is relied upon.
- Callers don't care about: distinction from `new`; they treat them as interchangeable.

### `VirtualAddress::into_raw_value(self) -> usize` (trait `Address`)
- Callers assume: returns the exact `usize` used to construct the address — the inverse
  of `new` / `from_raw_value`. This is the single most-used operation (102 sites) and is
  the basis for nearly all address arithmetic: offsets (`dst.into_raw_value() -
  vaddr.into_raw_value()`), bounds (`addr.into_raw_value().checked_add(size-1)`),
  alignment (`align_down(addr.into_raw_value(), PAGE_ALIGNMENT)`), and conversion to
  raw pointers (`info.base().into_raw_value() as *mut u8`), and virt→phys translation
  (`virt_to_phys(dst.into_raw_value())`).
- Callers assume `into_raw_value` is a pure observation: it does not consume/alter any
  resource (the address is `Copy`), and repeated calls yield the same value.
- Callers don't care about: how the `usize` is stored internally, only that it equals
  the construction value.

## Abstract Resource

`VirtualAddress` is a **thin, infallible newtype over a pointer-sized integer (`usize`)
representing a location in a virtual address space**. From the caller's perspective it
*is* its raw `usize` value — it carries no extra state, ownership, or invariant; it only
adds type-safety (distinguishing virtual from physical/frame addresses) and a small set
of address-arithmetic conveniences.

## Key Invariants (caller perspective)

- **Round-trip / faithful storage:** for all `a: usize`,
  `VirtualAddress::new(a).into_raw_value() == a` and
  `VirtualAddress::from_raw_value(a).into_raw_value() == a`. This is the core property
  every arithmetic caller depends on, so the View must be `int`/`usize`-valued and
  satisfy `new(a)@ == a` and `into_raw_value(x) == x@`.
- **`new` and inherent `from_raw_value` are equivalent and infallible** — both just store
  the value; every `usize` is a valid virtual address (`max_addr == usize::MAX`).
- **`into_raw_value` is a pure, non-consuming observation** — `VirtualAddress` is `Copy`,
  so reading the raw value neither mutates nor invalidates the address.
- **Order/equality agree with the underlying integer** — `Ord`/`Eq` on `VirtualAddress`
  match comparison of `into_raw_value()`, which callers rely on for range/bounds checks.
