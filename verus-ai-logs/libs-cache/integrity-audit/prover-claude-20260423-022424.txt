### Finding 1: `DerefMut` is missing from the audit (Severity: Medium, Non-blocking)

**Lines 102–106 of `lib.rs`**: `impl<V> DerefMut for CacheGuard<'_, V>` has **no `#[verus_verify]` attribute and no spec**. It is implicitly external — Verus ignores it entirely. Your audit enumerates every `external_body` item but misses this implicitly-excluded function.

**Why it matters**: `DerefMut` allows callers to **mutate the cached value** through the guard (`*guard = new_value`). The `get` spec commits to `self@ == old(self)@.spec_get(*key).0`, which says `contents` is unchanged (only `lru_order` changes). But mutations through DerefMut modify the entry's value in the underlying BTreeMap. When the guard is dropped and `self` becomes accessible again, the actual `contents[key]` may differ from what the spec claims.

This is partially mitigated by: (a) `get` is already external_body (the postcondition is trusted regardless), (b) CacheGuard's `view()` is uninterpreted so verified code can't derive contradictions, and (c) the mutable borrow prevents concurrent cache operations while the guard is alive. But it should be **explicitly enumerated** in your cheating count as an implicitly-external item, because it's exec code outside the verification boundary that can invalidate spec claims.

**Recommendation**: Add `DerefMut` to your audit inventory with classification "IMPLICITLY_EXTERNAL — no `#[verus_verify]`, mutation through guard not modeled in spec."

### Finding 2: `u64` counter overflow is an unguarded soundness gap (Severity: Low, Non-blocking)

**Lines 210, 246, 257 of `lib.rs`**: `self.counter += 1` inside the external_body functions `get` and `put` has no overflow check. The counter is `u64`, so overflow is practically impossible (~585 years at 1 billion ops/sec). However:

- In **debug builds**: Rust panics on overflow — the external_body spec postcondition would be vacuously true (unreachable), but the program crashes.
- In **release builds**: Rust wraps to 0 — the newly accessed entry gets `last_used = 0`, making it appear to be the *oldest* entry, **inverting LRU ordering**. The external_body specs assert postconditions (e.g., `self@ == old(self)@.spec_get(*key).0`) unconditionally, without a precondition like `self.counter < u64::MAX`.

This is within the external_body trust boundary, so it's not a Verus verification bug, but it's a **missing precondition** on the trusted specs that should be documented in your trust surface analysis.
