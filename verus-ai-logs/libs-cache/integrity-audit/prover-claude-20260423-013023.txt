## Critique

Your analysis is thorough and demonstrates deep understanding of the Verus verification landscape for this module. The conclusions are largely sound. However, I found several issues — one is a substantive accuracy problem, and the others are analytical gaps worth addressing.

### Issue 1: assume_specification for `insert` and `len` axiom are NOT semantically identical to upstream (Blocking)

**Severity: Blocking — this is a factual error in the analysis that affects trust documentation.**

You claim the 5 `assume_specification` items are "semantically identical — only the import path differs." This is incorrect for two of them.

**Upstream vstd `insert` spec** (`btree.rs:624-637`):
```rust
ensures
    obeys_cmp_spec::<Key>() ==> {
        &&& m@ == old(m)@.insert(k, v)
        &&& match result { ... }
    },
```

**Your local `insert` spec** (`lib.vstd_btree.rs:108-122`):
```rust
ensures
    btreemap_view_spec(*m) == btreemap_view_spec(*old(m)).insert(k, v),
    match result { ... },
```

Your local spec **drops the `obeys_cmp_spec::<Key>()` guard**, making the ensures unconditional. The same is true for `axiom_spec_btree_map_len` — upstream guards with `key_obeys_cmp_spec::<Key>()`, your local version does not.

This means your specs are **strictly stronger** than upstream. They silently assume `obeys_cmp_spec` holds for any `K: Ord`, which is true for well-behaved types but is an additional trust assumption not present in the originals. Your trust.md and fix_report.md must document this deviation rather than claiming the specs are identical copies. The practical risk is low (any sane `Ord` impl satisfies `obeys_cmp_spec`), but an integrity audit should not have factual errors about what it trusts.

**Recommendation:** Add a note in `trust.md` under the assume_specification section stating: "The local `insert` and `len` axiom specs drop the upstream `obeys_cmp_spec`/`key_obeys_cmp_spec` precondition guard, unconditionally assuming the Ord implementation is well-formed. This is a deliberate strengthening that removes a proof obligation on callers at the cost of an additional trust assumption."

### Issue 3: Your `put` trade-off analysis is correct but under-justified (Non-blocking)

You correctly conclude that rewriting `put` to avoid `get_mut` isn't worth it. But your reasoning ("would require a new `axiom_cache_lru_of_insert`") could be stronger. The deeper reason is:

The existing-key path in `put` does in-place mutation via `get_mut`: it updates `entry.value` and `entry.last_used` without removing/reinserting. A `remove`+`insert` rewrite wouldn't just need an LRU axiom — it would also need to prove that the counter-based ordering is preserved through the remove-reinsert cycle. With `cache_lru_of` being uninterpreted for non-empty maps, you'd likely need **two** new axioms: one for how insert affects `cache_lru_of`, and one relating the fresh counter value to MRU position. The net trust cost is worse than the current single `external_body` on `put`. This stronger justification should go into your report.

### Issue 4: On `find_lru_victim` for-loop rewrite — your instinct is right, be more decisive (Non-blocking)

You characterize the trade-off as "1 external_body for ~3 assume_specifications" and call it "arguably an improvement." I'd argue the opposite: it's arguable that it's **not** an improvement, and you should say so definitively.

An `external_body` on a 3-line function whose body is `entries.iter().min_by_key(|(_, e)| e.last_used).map(|(k, _)| k.clone())` is highly auditable — the entire trust surface is visible in one glance. Replacing it with ~3 `assume_specification` items for BTreeMap iterator infrastructure copies from vstd spreads the trust surface across multiple declarations that must be kept in sync with upstream. The net formal trust count goes up (3 > 1), and the informal auditability arguably gets worse.

**Recommendation:** State clearly that the current approach is preferable and close this item.
