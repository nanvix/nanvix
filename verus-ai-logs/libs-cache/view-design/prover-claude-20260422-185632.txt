## 1) Three fields vs two
**Verdict:** `contents + capacity + lru_order` is the better abstraction.

- **Why it works:** exact LRU order is caller-observable through future evictions, so `lru_order: Seq<K>` passes the substitution test.
- **Why `Map<K, nat>` is worse:** it introduces arbitrary ranking numbers, plus extra invariant burden (injective, range-bounded, probably dense). That is more algorithm-shaped, not more abstract.

**Recommendation:** keep `lru_order: Seq<K>`.

## 2) CacheGuard not modeled separately
**Severity: blocking**

This is the main flaw.

Your current `spec_get(self, key) -> (CacheView, Option<V>)` models a **value read**, but the real API returns a **mutable borrowed handle**. That means your design cannot express:

- mutation through the guard,
- persistence of that mutation after guard drop,
- the temporary borrowing relationship between cache and guard.

So caller expectation **“Guard provides mutable access; changes persist”** is **not actually specifiable** with the current design.

**Recommendation:** model `get` as producing a separate logical guard/token/view. Typical shape:

- cache view after recency update, plus
- `Option<GuardView<K, V>>` or equivalent borrow token.

A good abstraction is often:
- cache state with the borrowed entry logically removed or reserved, and
- guard state carrying the borrowed key/value and enough info to reinsert on drop.

Without this, your spec is incomplete for the public API.

## 3) `filter(...).push(key)` for MRU update
**Verdict:** semantically reasonable, but proof-hostile.

The issue is not correctness; it’s that `Seq::filter` with a lambda is often awkward for SMT reasoning. You will likely keep reproving facts like:

- set preserved,
- no duplicates preserved,
- last element is `key`,
- all other order relationships unchanged.

**Recommendation:** define a named helper spec like `move_to_mru(order, key)` and prove lemmas about it once.  
That gives you a clean abstraction boundary and avoids spreading `filter` reasoning everywhere.

## 4) `inv()` completeness
**Severity: moderate**

Your invariant is logically close, but **too weak for easy verification**.

You currently have:
- domain size bounded by capacity,
- no duplicates in `lru_order`,
- same key set in `lru_order` and `contents`.

What is missing in practice is an explicit cardinality/link fact such as:

```rust
&&& self.lru_order.len() == self.contents.dom().len()
```

This is derivable from your current invariant, but Verus may not derive it automatically when you need:
- nonemptiness of `lru_order`,

- size preservation after overwrite/remove.

**Recommendation:** add the explicit length equality.

Also, your transition functions should probably have `recommends self.inv()` (or equivalent discipline), since they rely on well-formedness.
