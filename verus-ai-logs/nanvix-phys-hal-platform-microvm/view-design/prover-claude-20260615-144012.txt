The honest conclusion is that the View should reflect this: it's essentially a unit type with no fields, since there's no mutable state to capture. The meaningful abstraction is the pure spec function itself, which defines what the translation should do mathematically. I'm defining a spec function that captures the address-translation behavior as a stateless, deterministic map.

But I need to be careful about what the spec function actually encodes. The caller doesn't strictly depend on identity—it depends on totality, purity, injectivity over page-aligned inputs, and valid address encoding. Those are the caller-observable properties that matter. The fact that MicroVM happens to use identity is an implementation detail; the spec should capture the abstract contract, not the concrete implementation.

So the cleanest approach is to define a stateless pure address-translation facet with those algebraic properties, and since there's no mutable state to abstract, the View becomes a unit type or isn't needed at all. I'll present it that way—explaining why a View with fields would violate minimality and the substitution principle. I'm weighing whether to make `spec_gva_to_gpa` open or closed. If I expose it as identity, the caller gets the strongest contract for reasoning about injectivity and frame-walking, but that locks the implementation to identity and prevents future swaps to offset-based translation. Keeping it closed would hide the exact mapping and let the platform evolve later, though the caller only truly needs injectivity and totality to function correctly.

But stepping back — this is the MicroVM platform where identity is a hardware fact, not an implementation detail. The substitution test is about algorithm rewrites, not platform changes, so an open identity spec is correct and robust. The caller's analysis confirms it doesn't actually depend on identity for correctness, just for the specific MicroVM realization, so exposing identity as a proven property rather than hiding it behind abstraction makes sense here.

For the View design itself, I'm settling on a stateless unit type since `gva_to_gpa` is pure — there's no mutable state to track. I'll define `spec_gva_to_gpa` as an associated spec function on the View that simply returns the input unchanged. The invariant is trivially satisfied, and I can derive the caller-facing properties like injectivity and totality as consequences of identity. I'm also rejecting field candidates like `physical_memory_layout` since the translation function makes no claims about memory coverage — that's the caller's responsibility via `is_covered` — so including it would violate minimality and over-constrain the spec.
