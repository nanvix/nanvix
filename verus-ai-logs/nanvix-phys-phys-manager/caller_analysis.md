## Trait Obligations
None. `PhysMemoryManager` implements no traits relevant to dispatch
(`Drop`/`GlobalAlloc`/`Iterator` etc.). All usage is direct method calls on the
singleton. The frame ownership wrappers it returns (`KernelFrame`, `UserFrame`)
*do* carry `Drop` semantics (dropping frees the frame), and callers depend on
that — see below.

## Internal Call Graph
- `alloc_many_user_frames` → `check_user_watermark(count)` → `frame::free_count`,
  `config::kernel::KERNEL_WATERMARK`, then `self.upool.alloc()` per frame.
- `alloc_user_frame` → `check_user_watermark(1)` → `self.upool.alloc()`.
- `alloc_kernel_frame` → `frame::alloc` → `KernelFrame::new` (frees the frame on
  wrap failure).
- `alloc_many_kernel_frames` → `frame::alloc_contiguous(count)` →
  `KernelFrame::new` per frame (frees the leftover contiguous range on failure).

Key structural fact for the View: **user** allocations flow through `Upool`
(`self.upool`) and are watermark-gated; **kernel** allocations go straight to the
`frame` allocator and bypass the watermark.

## Caller Expectations

### `init(upool) -> Result<(), Error>`
Single caller: `mm/phys/mod.rs::init`, exactly once during single-threaded boot,
immediately after `Upool::new()`. Followed by `proof!{ lemma_manager_ready(); }`.
- Callers assume (Ok): the manager singleton now exists and holds the provided
  `upool`; subsequent `get_mut()` will not panic; the subsystem reaches the
  `manager_ready` / `live()` state. This is the post-state the surrounding
  `phys::init` spec advertises (`phys_view().live()`).
- Callers assume (Err): only `InvalidArgument`, and only on double-init; boot
  treats this as fatal (propagated with `?`).
- Callers don't care about: the `MaybeUninit` storage, the `AtomicBool` init
  flag, or the atomic ordering. They care only that "after Ok, the manager is
  ready and frame guarantees become meaningful."

### `alloc_kernel_frame(&mut self) -> Result<KernelFrame, Error>`
Callers: `new_vmem` (page-directory frame), two `page_table_allocator` closures
(`link_user_pages`, `alloc_upages`), and `alloc_kpage`.
- Callers assume (Ok): a `KernelFrame` owning one freshly allocated physical
  frame that no one else holds. They immediately `clear()` it, wrap it in a
  `KernelPage`, or build a page table on it. Ownership/Drop semantics matter:
  dropping the returned frame must free it.
- Callers assume (Err): nothing was allocated and no frame leaked (the impl
  frees the frame if `KernelFrame::new` fails); error is simply propagated with
  `?`. **No watermark involvement** — kernel allocation must succeed whenever a
  physical frame is available, even below `KERNEL_WATERMARK`.
- Callers don't care about: the exact physical address chosen, or the
  `frame::alloc` + wrap mechanics.

### `alloc_many_kernel_frames(&mut self, count, &mut Vec<KernelFrame>) -> Result<(), Error>`
Single caller: `alloc_kpages`. Caller pre-checks the vector is empty and has
capacity ≥ `count`, then optionally `clear()`s each frame; on a later clear
failure it `clear()`s the whole vec to free everything.
- Callers assume (Ok): exactly `count` frames are pushed, and they are
  **physically contiguous** (the documented reason: identity-mapped kernel
  stacks). Each entry is an owning `KernelFrame`.
- Callers assume (Err): the vector is left empty (the impl `clear()`s it and
  frees any un-wrapped frames from the contiguous run); nothing leaks. Watermark
  is bypassed.
- Callers don't care about: how contiguity is obtained
  (`frame::alloc_contiguous`) or the base-address arithmetic.
- Precondition relied upon by the impl (and satisfied by the caller): `frames`
  empty and `capacity ≥ count`.

### `alloc_many_user_frames(&mut self, count, &mut Vec<UserFrame>) -> Result<(), Error>`
Single caller: `alloc_upages` (L611). Caller defensively `uframes.clear()`s on
error, then drains the vec to map each frame.
- Callers assume (Ok): exactly `count` `UserFrame`s pushed; **not** required to
  be contiguous (they are mapped individually at successive virtual addresses).
- Callers assume (Err): `uframes` is emptied (impl `clear()`s on per-frame
  failure); request is **watermark-gated** — it is rejected with `OutOfMemory`
  if fulfilling it would drop free frames below `KERNEL_WATERMARK`. This is the
  central guarantee distinguishing user from kernel allocation.
- Callers don't care about: pool internals (`Upool::alloc`) or which frames are
  handed out.
- Precondition relied upon: `frames` empty and `capacity ≥ count`.

### `alloc_user_frame(&mut self) -> Result<UserFrame, Error>`
Single caller: CoW page-fault resolution in `vmem.rs:879`. The frame is filled
via `memcpy`, installed into a PTE, then `leak()`ed (ownership transferred to the
page table).
- Callers assume (Ok): one `UserFrame` with a valid `address()`, subject to the
  **same watermark check** as `alloc_many_user_frames` (count = 1). Must be a
  fast path with no intermediate `Vec`.
- Callers assume (Err): nothing allocated; propagated with `?`. On the hot CoW
  path, `OutOfMemory` from the watermark is the expected rejection.
- Callers don't care about: the watermark threshold value itself, only that the
  single-frame path enforces it identically to the bulk path.

### `check_user_watermark(count)` (private)
No external callers. It is the shared gate for the two user-allocation paths and
encodes the invariant "after any user allocation, at least `KERNEL_WATERMARK`
frames remain free for the kernel." Relevant to the View as the predicate behind
the user-vs-kernel asymmetry; not part of the public contract.

## Abstract Resource
`PhysMemoryManager` is the singleton broker over the pool of physical page
frames. It hands out **typed, owning frame handles**: `KernelFrame`s (drawn
straight from the frame allocator, contiguous on request, never watermark-gated)
and `UserFrame`s (drawn from the user `Upool` and gated by a kernel watermark so
the kernel always retains `KERNEL_WATERMARK` free frames). Callers observe a
partition of frames into allocated/free with per-frame refcounts (the existing
`FrameAllocView`), plus a liveness flag that the singleton is initialized
(`manager_ready` / `live()`), and never touch the underlying storage mechanisms.

## Key Invariants (caller perspective)
- **Init-before-use**: every alloc path runs only after `init` succeeded; until
  then `get_mut` panics. Callers rely on the subsystem being `live()`.
- **Kernel allocations bypass the watermark**; **user allocations are
  watermark-gated** and rejected (`OutOfMemory`) when they would drop free frames
  below `KERNEL_WATERMARK`. `alloc_user_frame` and `alloc_many_user_frames`
  enforce this identically (via `check_user_watermark`).
- **All-or-nothing bulk allocation**: on success the caller's vector holds
  exactly `count` owning handles (contiguous for kernel frames); on failure the
  vector is emptied and no frame leaks.
- **No leak on failure**: every error path frees frames already taken from the
  allocator (kernel wrap-failure free, contiguous-range cleanup, user-pool
  `clear`).
- **Ownership/Drop discipline**: returned `KernelFrame`/`UserFrame` own their
  physical frame; dropping frees it, `leak()` transfers ownership. Callers manage
  frame lifetime entirely through these handles.
- **Caller-supplied storage contract**: bulk APIs require the passed `Vec` to be
  empty with `capacity ≥ count`; otherwise `InvalidArgument`.

### Assessment
- Coverage: partial. The upstream work modeled subsystem *liveness*
  (`initialized` / `manager_ready` / `frames.wf()`) and reservation vocabulary on
  `FrameAllocView`, which is what `phys::init` needed. It did **not** specify the
  allocation operations.
- Strength: weak for this module's purpose. There is no spec expressing the
  watermark gate, the allocated/free refcount transitions per alloc, contiguity
  for kernel ranges, or the all-or-nothing/no-leak error behavior callers rely
  on. `PhysMemoryManager::init` being `external_body` with no ensures means the
  `manager_ready` transition is currently asserted only via `lemma_manager_ready`.
- View design: the existing `FrameAllocView` (allocated/free sets + refcounts) is
  caller-abstract and is the right basis for the alloc specs — it already exposes
  exactly what callers observe (which frames are taken, refcounts for CoW).
  Remaining work is to write per-function ensures over `phys_view().frames` for
  the six target functions; do **not** modify `FrameAllocView`, `Inner`,
  `frame_addr_of`, `byte_at_address`, or the `View for Inner` impl.
