## Trait Obligations
None. `PhysMemoryManager` implements no traits in scope (no `Drop`, `GlobalAlloc`,
`Iterator`, etc.). All call dispatch is direct, static method calls on the singleton.
The frames it hands out — `UserFrame` / `KernelFrame` — carry their own `Drop`
(refcount release / frame free), but that is the wrapper types' contract, not this
module's.

## Caller Expectations

### `init(upool) -> Result<(), Error>`
- **Callers assume (Ok):** the singleton is now established and live; every later
  `PhysMemoryManager::get_mut()` will succeed (not panic) and `alloc_*` operations are
  usable. Lifecycle flips `false → true` exactly once during single-threaded boot.
- **Callers assume (Err):** returned only when already initialized
  (`InvalidArgument`); boot treats this via `?` and aborts. The sole caller calls it
  exactly once, so the error path is effectively unreachable in practice.
- **Would break callers:** if a successful `init` did not guarantee subsequent
  `get_mut()`/`alloc_*` are valid (i.e. if the "initialized" guarantee were not
  established), or if it could be called twice and silently clobber the singleton.
- **Would NOT break callers:** the internal storage (`MaybeUninit` + `AtomicBool`
  gate), the `Upool` representation, ordering of the write vs. the flag — all opaque.
  Callers only observe "after Ok, the subsystem is initialized."

### `alloc_user_frame(&mut self) -> Result<UserFrame, Error>`
- **Callers assume (Ok):** a single, owned, fresh user frame backed by a distinct
  physical frame, **subject to the kernel watermark** (same gate as the many-frame
  path). The frame is not zeroed/contiguous-guaranteed; caller (`vmem.rs`) memcpys
  into it and then `leak()`s it into the page table. Refcount semantics of `UserFrame`
  apply.
- **Callers assume (Err):** nothing was allocated; no frame leaks; caller propagates
  via `?`. Failure includes watermark breach (`OutOfMemory`) and pool exhaustion.
- **Would break callers:** skipping the watermark check (the doc/comment at the call
  site explicitly relies on this single-frame helper keeping the watermark gate), or
  returning a frame that is not exclusively owned by the caller.
- **Would NOT break callers:** that it delegates to `Upool::alloc`; that it shares the
  `check_user_watermark(1)` helper. Only the "watermarked single owned frame or clean
  error" contract matters.

### `alloc_many_user_frames(&mut self, count, frames: &mut Vec<UserFrame>) -> Result<(), Error>`
- **Callers assume (preconditions):** they pass an **empty** `Vec` with **capacity ≥
  count**; both are validated (`InvalidArgument` otherwise). The `virt::manager.rs:611`
  caller pre-sizes `uframes` and, on any error, additionally `clear()`s it.
- **Callers assume (Ok):** `frames` now holds exactly `count` user frames (not
  guaranteed physically contiguous), all owned by the caller, allocation respected the
  kernel watermark. `count == 0` is a trivial success.
- **Callers assume (Err):** all-or-nothing — `frames` is truncated back to empty and
  any frames allocated mid-loop are released (via `Vec::clear` → `UserFrame::Drop`).
  No partial fills, no leaks.
- **Would break callers:** leaving `frames` partially filled on error, leaking frames,
  exceeding the watermark, or filling more/fewer than `count` on success.
- **Would NOT break callers:** non-contiguity is explicitly fine; the loop-and-push
  strategy and `Upool` internals are opaque.

### `alloc_kernel_frame(&mut self) -> Result<KernelFrame, Error>`
- **Callers assume (Ok):** one owned `KernelFrame` backed by a real physical frame,
  **bypassing the watermark** (no artificial ceiling — kernel allocations must always
  be servable when memory exists). Callers wrap it in `KernelPage`, optionally
  `clear()` it (frame is not guaranteed zeroed), and build page directories/tables.
- **Callers assume (Err):** nothing allocated, no leak; the helper already frees the
  raw frame if `KernelFrame::new` fails. Caller propagates via `?`.
- **Would break callers:** applying the user watermark to kernel allocations (would
  starve page-table/page-directory allocation under memory pressure), or leaking a
  frame when `KernelFrame::new` fails.
- **Would NOT break callers:** the alloc→wrap→free-on-wrap-failure mechanics are
  internal; callers only need "owned kernel frame or clean error, no watermark."

### `alloc_many_kernel_frames(&mut self, count, frames: &mut Vec<KernelFrame>) -> Result<(), Error>`
- **Callers assume (preconditions):** empty `Vec` with capacity ≥ count (validated,
  `InvalidArgument` otherwise). `alloc_kpages` (`virt::manager.rs:748`) enforces this
  itself before calling.
- **Callers assume (Ok):** `frames` holds exactly `count` **physically contiguous**
  kernel frames (ascending by `PAGE_SIZE`), watermark bypassed. Contiguity is the
  load-bearing guarantee — kernel stacks rely on a linear identity-mapped region.
- **Callers assume (Err):** all-or-nothing — `frames` cleared, every frame from the
  contiguous block freed (both already-wrapped via `Drop` and not-yet-wrapped via
  explicit `frame::free`), no leaks.
- **Would break callers:** non-contiguous frames on success, partial fills, or any
  leak on the error path; applying a watermark.
- **Would NOT break callers:** the base-address + offset wrapping loop and the
  two-phase cleanup are internal details.

### `check_user_watermark(count) -> Result<(), Error>` (private)
- **Internal callers** (`alloc_user_frame`, `alloc_many_user_frames`) assume: `Ok`
  iff `free_count() >= KERNEL_WATERMARK + count` (with `count==0` / overflow handled —
  `KERNEL_WATERMARK + count` overflow yields `InvalidArgument`); `Err(OutOfMemory)`
  when the request would drop free frames below the watermark. It is a pure gate with
  no side effects on allocator state.
- Not part of any external contract; exists only to share the watermark policy between
  the single- and many-frame user paths.

## Abstract Resource
`PhysMemoryManager` is the kernel's **single global owner of physical RAM frames**. It
hands out ownership of individual physical frames in two qualities of service: **user
frames** (refcounted, watermark-gated, possibly non-contiguous, drawn from `Upool`) and
**kernel frames** (watermark-exempt, single or physically-contiguous runs, drawn
directly from the `frame` allocator). Callers care only about: *did I get the exact
frames I asked for, owned cleanly, with the right contiguity/watermark policy — and on
failure, is the allocator left untouched with nothing leaked?*

## Key Invariants (caller perspective)
- **Lifecycle:** usable only after a successful `init`; `init` is one-shot/monotonic
  (second call errors, never clobbers). `get_mut` is valid exactly when initialized.
- **Ownership / no double-allocation:** each successful allocation yields frames the
  caller exclusively owns; the same physical frame is never handed to two live owners.
  User frames additionally carry refcount semantics for CoW sharing.
- **All-or-nothing on bulk ops:** `alloc_many_*` either fully succeed (vector holds
  exactly `count`) or fully roll back (vector empty, every interim frame freed). No
  partial states, no leaks.
- **Policy split:** user allocations are gated by `KERNEL_WATERMARK`
  (`free_count() >= KERNEL_WATERMARK + count`); kernel allocations bypass it entirely.
- **Contiguity contract:** `alloc_many_kernel_frames` guarantees physical contiguity;
  `alloc_many_user_frames` makes no such promise.
- **Caller-provided storage discipline:** bulk APIs require an empty, sufficiently
  pre-reserved `Vec`; they validate and reject otherwise (`InvalidArgument`) rather
  than reallocating.

## Notes for View Design
- The natural abstract state is already largely present upstream in
  `mm::phys::mod.spec.rs` (`PhysMemView { initialized, frames: FrameAllocView }` with
  `allocated_frames` / `free_frames` / `refcounts`, plus `phys_view()`). These are
  **do-not-modify** existing definitions and form the obvious anchor:
  - `init`'s post-state ↔ `initialized` flips on (`spec_initialize`).
  - `alloc_*` move frames `free → allocated` (refcount → 1) — analogous to
    `spec_book_frame` / `spec_book_frames`, but driven by allocation rather than
    booking.
  - the watermark gate is expressible against `free_frames` cardinality vs.
    `KERNEL_WATERMARK + count`.
- The View must NOT expose `Upool` internals, `MaybeUninit`/`AtomicBool` storage, or
  the loop/cleanup mechanics — no caller observes them. Stick to: initialized flag,
  free/allocated frame sets, refcounts, and the contiguity/watermark policy.
