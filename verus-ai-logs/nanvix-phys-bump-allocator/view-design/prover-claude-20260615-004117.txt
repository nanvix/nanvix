[THINKING] Now I'm thinking through what state a caller needs to track when using this resource—specifically how many slots have been allocated so far, which lets them reason about uniqueness and whether the pool is exhausted.

The core mutable state is just the bump index tracking which slot comes next. From the caller's perspective, what really matters is how many slots have been consumed versus the total capacity. The key insight is that any one-shot fixed-capacity allocator needs to track "how many have been handed out," and that abstraction holds regardless of the underlying implementation details like whether we use a bump pointer or free list.

For expressing non-aliasing to the caller, I can model the allocator as vending slot indices sequentially—each allocation gets the current count, then the count increments. Distinct indices automatically map to disjoint memory regions through the deterministic address calculation, which is an implementation detail captured in the type invariant rather than the View itself.

So the View should be minimal: track the number of slots already allocated and the total capacity. The question is whether unit_size and unit_align belong in the View, since they gate which types can be allocated but are already known statically to the caller through const generics. I'm settling on a minimal view that captures just the mutable state: `allocated` (how many slots have been vended) and `capacity` (the fixed maximum). The key insight is that uniqueness and non-aliasing are enforced by the fact that each allocation returns a distinct slot index equal to the old allocated count, making it impossible for two callers to receive the same slot. The contract should express that each returned slot corresponds to a unique index from the monotonic counter, and the type invariant ensures distinct indices map to disjoint memory regions. I'm deciding whether to include `capacity` as a View field or reference it directly from the const generic—keeping both `allocated` and `capacity` in the View makes the spec self-contained and cleaner than reaching into trait constants.
