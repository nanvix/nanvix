  being the *sole* and *complete* deallocation step — they do not free the frame
  themselves once it has been wrapped in a `KernelFrame`.

## Caller Expectations

### `KernelFrame::new`
- Callers assume: on `Ok(kf)`, the handle owns the *same* physical frame that was
  passed in — `kf@ == base@`. The input `base` is always a valid, page-aligned
  address obtained from a successful `frame::alloc()` / `alloc_contiguous()`
  (i.e. `base.inv()` holds).
- Callers assume: on `Err(_)`, `new` did **not** take ownership / did not free the
  frame — the caller is responsible for freeing `base` (it does so explicitly).
  No state guarantee beyond "the wrap failed".
- Callers don't care about: the identity-mapping side effect
  (`mm::virt::identity_map_page`), how page tables are installed, or any internal
  representation beyond the abstract address.

### `KernelFrame::drop`
- Callers assume: dropping frees the underlying physical frame exactly once via
  the global allocator, with no further action required from them.
- Callers don't care about: error handling inside drop (a failed free is only
  logged), or the mechanics of `frame::free`.

### `KernelFrame::base`
- Callers assume: `base()` is a pure, side-effect-free accessor returning the
  frame's `FrameAddress`, equal to the construction address (`result@ == self@`),
  and page-aligned so downstream page/virtual-address conversions are valid.
- Callers don't care about: how `base` is stored internally (field vs. computed).

## Abstract Resource
`KernelFrame` is an **owning handle to a single page-sized physical frame** that
is identity-mapped for kernel access. The module manages the ownership lifecycle
of one physical frame: `new` wraps a freshly allocated frame address into an
owning handle, `base` exposes that frame's physical address, and `drop` returns
the frame to the global frame allocator. Its `View` is the physical address
(`int`) of the owned frame.

## Key Invariants (caller perspective)
- A `KernelFrame`'s abstract view is its physical frame address and never
  changes for the lifetime of the handle: `self@ == base@` from construction,
  and `base()` reports the same value.
- `new` preserves the input address on success (`kf@ == base@`) and does not
  consume the frame on failure.
- Each physical frame is owned by at most one live `KernelFrame`; dropping the
  handle frees that frame exactly once. Callers never double-free a wrapped frame.
- `base()` is pure: it does not mutate the handle or the allocator and returns a
  page-aligned `FrameAddress`.

### Assessment
- Coverage: **partial** — only `new` is specified (what the manager needed for
  `lemma_kernel_alloc_one`). `base` and `drop` are unspecified.
- Strength: **adequate for `new`'s success path** (`kf@ == base@`), but the
  `Err(_) => true` ensures is weak; callers actually rely on the implicit
  contract that `new` does not free/consume the frame on failure (currently
  guaranteed only by `external_body` + manual free at the call site).
- View design: **caller-abstract** — `type V = int` (physical address) matches
  exactly what every caller uses (`kf@`, address comparisons, `kernel_addr_set`,
  `into_page_address`). It does not leak internal representation, so it is a good,
  stable abstraction.

### Recommendations for View/spec design
- Keep `View::V = int` (the physical frame address) — all callers agree on this.
- Add a spec to `base`: `ensures result@ == self@` (pure accessor) so `kpage`
  conversions verify.
- Consider a spec for `drop` capturing the "frees the frame once" effect, so the
  manager error-path and stack teardown can reason about allocator state.
